# Пилот: папка реальных документов на новом сервере Ubuntu

Цель: прогнать настоящие документы, посчитать выдачу и отказы по причинам, вручную проверить каждый выданный DOCX.
Сервер: Ubuntu 22.04 или новее, 1 ядро и больше, от 4 ГБ ОЗУ, интернет не обязателен.

## 1. Подготовить образ (на ноутбуке, один раз)

```sh
cd ~/dre && docker build -t dre:1 .
docker save dre:1 | gzip > dre-1.tar.gz
scp dre-1.tar.gz user@server:~/
```

## 2. На сервере (один раз)

```sh
sudo apt-get install -y docker.io                # если Docker ещё не стоит
sudo usermod -aG docker $USER && newgrp docker
docker load < ~/dre-1.tar.gz
docker run --rm --cpus=1 dre:1 selfcheck     # в конце должно быть «OK»; запомните множитель speed.factor
```

Если самопроверка пишет не «OK», пришлите её вывод целиком.

## 3. Прогон папки

```sh
mkdir -p ~/pilot/in ~/pilot/out
# скопировать документы в ~/pilot/in (можно с подпапками): PDF, JPEG, PNG, WEBP, HEIC
docker run --rm --cpus=1 --user $(id -u):$(id -g) \
    -v ~/pilot:/data dre:1 batch /data/in /data/out
```

`--cpus=1` — как на целевом сервере, время тогда честное. Длинные сканы на медленном ядре могут
получить отказ `estimated_time_over_budget` (не успеть за 45 с) — это видно в сводке.
Прогон можно прервать и запустить снова: готовые документы пропускаются.

## 4. Что получится

```
~/pilot/out/<имя>.docx            выданные документы
~/pilot/out/_refused/<имя>.pdf    отказы: копия исходника
~/pilot/out/_refused/<имя>.json   причина отказа, время
~/pilot/out/journal.jsonl         строка на каждый документ
```

## 5. Быстрый подсчёт

```sh
docker run --rm -v ~/pilot:/data dre:1 summary /data/out
```

```
Документов: 120
Выдано:     53 (44%)
Отказов:    67 (56%)
    31  low_resolution
    22  unreliable_text
     9  unrecognized_text
     …
Время, с: медиана 3.8, максимум 21.4

На проверку (выданные DOCX):
  приказ_12.docx    <- приказ_12.pdf
  …
```

Причины отказов расшифрованы в `DEPLOY.md`, раздел 7. Самые частые:
- `low_resolution` — буквы мельче 8 px, скан меньше 300 dpi или фото издалека;
- `unreliable_text` — есть слова, прочитанные ненадёжно (в JSON отказа, поле `details.words`).

## 6. Ручная проверка выданных DOCX

Главный вопрос пилота: есть ли среди выданных документов хоть один с ошибкой.
Каждый DOCX открыть в Word рядом с исходником и отметить в таблице `~/pilot/проверка.csv`:

```
файл;итог;что не так
приказ_12.docx;ок;
письмо_3.docx;ошибка;«2024» вместо «2021» в дате
письмо_7.docx;вид;текст верный, съехала таблица
```

- `ок` — текст и вид в порядке;
- `ошибка` — неверное слово, цифра, пропущенная строка (это «плохая выдача», главное, что ищем);
- `вид` — текст верный, но оформление заметно хуже исходника.

Заготовка таблицы со всеми выданными файлами:

```sh
(echo "файл;итог;что не так"; ls ~/pilot/out/*.docx | xargs -n1 basename | sed 's/$/;;/') > ~/pilot/проверка.csv
```

## 7. Что прислать

1. `~/pilot/out/journal.jsonl` и вывод `summary`;
2. `~/pilot/проверка.csv`;
3. исходники всех документов с пометкой `ошибка` и 5–10 отказов, которые, по-вашему, должны были выдаться
   (если документы нельзя выносить — хотя бы JSON из `_refused/` и описание).
