# Развёртывание Document Reconstruction Engine

Модуль превращает PDF, скан или фото документа в редактируемый DOCX. Если модуль не уверен в результате,
он отказывает с кодом и причиной; документ с ошибками не выдаётся.

## 1. Требования к машине

| | целевой сервер | минимум |
|---|---|---|
| Процессор | 1 ядро x86-64 (Xeon) | 1 ядро x86-64 (2015+) |
| Память | 128 ГБ (память не ограничение) | 4 ГБ (ОС + 1 исполнитель; без запасного исполнителя) |
| Лимит памяти контейнера | не задавать (`--cpus=1` без `--memory`) | `--memory=2g` (пик процесса 1.3 ГБ) |
| Диск | 1.5 ГБ (образ) + входные и выходные файлы | то же |
| GPU / сеть | не нужны, всё работает офлайн | — |

Модели OCR, словари и списки слов загружены в исполнителе постоянно («тёплый пул»); на 1 ядре работает
один документ за раз и ещё один тёплый запасной исполнитель (при памяти от ~6 ГБ), который сразу берёт
работу, если первый остановлен по сроку.

Время на одном ядре эталонного ноутбука (после оптимизации 26.09): скан 1 стр. — 2.7 с, 3 стр. — 8.6 с,
7 стр. — 18.9 с, 10 стр. — 26.5 с; обычный PDF с текстовым слоем — 0.1–0.5 с. Серверный Xeon на ядро
может быть медленнее — модуль измеряет это при старте (раздел 11).

Время на одном ядре (эталонный ноутбук): обычный PDF с текстовым слоем — 0.1–0.5 с на документ,
скан/фото — 3–8 с на страницу. Предел — 45 с на документ, не больше 10 страниц (`DRE_MAX_PAGES`).

## 2. Установка

### Docker (основной способ)

```sh
docker build -t dre:1 .                       # из корня репозитория
docker run --rm --cpus=1 dre:1 selfcheck
```

Без интернета на сервере: собрать на машине с интернетом и перенести образ файлом.

```sh
docker save dre:1 | gzip > dre-1.tar.gz       # на машине сборки
docker load < dre-1.tar.gz                    # на сервере
```

Проверка образа одной командой (сборка, самопроверка на 1 ядре, побайтная сверка DOCX
с установкой без Docker): `deploy/docker-check.sh`. Из WSL без интеграции Docker Desktop:
`DOCKER=".../docker.exe" deploy/docker-check.sh` (файлы передаются в контейнер потоком, без монтирования).

### Без Docker (Ubuntu/Debian)

```sh
sudo deploy/install.sh            # ставит в /opt/dre, команды — в /usr/local/bin
```

Скрипт ставит пакеты (Tesseract и модели, словари Hunspell ru/kk/uz/en, шрифты Liberation, Python),
создаёт окружение `/opt/dre/venv`, строит списки слов в `/opt/dre/lexicon` и запускает самопроверку.
Одинаковый с Docker результат гарантирован на тех же версиях пакетов (Ubuntu 26.04, Tesseract 5.5.0);
при другой версии скрипт предупреждает.

## 3. Запуск

| что | Docker | без Docker |
|---|---|---|
| HTTP-сервис на порту 8080 | `docker run -d --restart=unless-stopped -p 8080:8080 -e DRE_API_KEY=… --cpus=1 dre:1` | `DRE_API_KEY=… DRE_BIND=0.0.0.0:8080 dre-serve` |
| один файл | `docker run --rm --user $(id -u):$(id -g) -v $PWD:/data dre:1 convert /data/a.pdf --output /data/a.docx` | `dre-convert a.pdf --output a.docx` |
| папка | `docker run --rm --user $(id -u):$(id -g) -v $PWD:/data dre:1 batch /data/in /data/out` | `dre-batch in out` |
| сводка по папке | `docker run --rm -v $PWD:/data dre:1 summary /data/out` | `dre-summary out` |
| самопроверка | `docker run --rm dre:1 selfcheck` | `dre-selfcheck` |

`--user $(id -u):$(id -g)` — чтобы результаты в смонтированной папке принадлежали вам, а не пользователю контейнера.
Сервис готов через 5–10 с после старта (загрузка моделей и калибровка скорости); до этого `/ready` отвечает 503.

## 4. Самопроверка

`selfcheck` проверяет Tesseract и модели, словари, списки слов, шрифты, ядра и память, измеряет скорость
машины и прогоняет 6 контрольных файлов: обычный PDF, три скана (ru, kk, узбекская латиница) и фото листа
под углом со сверкой текста с эталоном, фото низкого разрешения, на котором должен быть отказ. Вывод на английском;
в конце печатает «OK» или список проблем (PROBLEMS); код возврата 0 или 1. Запускать после установки, обновления и переноса на новую машину.

## 5. Пакетный режим (папка)

`batch IN OUT` обрабатывает все PDF, JPEG, PNG, WEBP и HEIC из папки `IN`, включая подпапки:

- `OUT/<имя>.docx` — выданные документы; для файлов из подпапок имя собирается так: `a/b/x.pdf` → `a__b__x.docx`;
- `OUT/_refused/` — отказы: копия исходного файла и `<имя>.json` с кодом, причиной и временем (`--refused DIR` задаёт другую папку);
- `OUT/journal.jsonl` — по строке на документ: файл, итог, причина, секунды, страницы.

`summary OUT` — сводка по журналу: выдано, отказы по причинам, время, список выданных DOCX для проверки.
При повторном запуске уже обработанные файлы пропускаются (`--again` — обработать заново).
`--workers N` — сколько документов обрабатывать одновременно; больше числа ядер ставить нет смысла (на 1 ядре — 1).

## 6. API

Все ответы содержат заголовок `X-Request-ID`.

| запрос | ответ |
|---|---|
| `GET /health` | 200 `{"status": "alive"}` — процесс жив |
| `GET /ready` | 200 — готов принимать документы, 503 — ещё загружается или нет `DRE_API_KEY`. В теле: языки OCR, `ocr_capabilities.speed` (калибровка), `page_threads` |
| `POST /convert` | тело — файл целиком (не multipart), до 20 МБ |

Запрос на конвертацию:

```sh
curl -H "Authorization: Bearer $DRE_API_KEY" -H "Content-Type: application/pdf" \
     --data-binary @letter.pdf -o letter.docx http://server:8080/convert
```

`Content-Type`: `application/pdf`, `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif`.

Успех: 200, тело — DOCX (`application/vnd.openxmlformats-officedocument.wordprocessingml.document`),
заголовок `X-Conversion-MS` — время на сервере.

Отказ или ошибка: JSON

```json
{"error": {"code": "UNREADABLE_DOCUMENT", "message": "…", "stage": "qa", "request_id": "…",
           "details": {"page_index": 0, "reason": "unreliable_text", "words": "…"}},
 "metrics": {"total_ms": 4120.5, "pages_total": 1}}
```

## 7. Коды отказов

| HTTP | `code` | что значит | что делать |
|---|---|---|---|
| 400 | `INVALID_PDF` | не PDF и не картинка, файл повреждён, пустое тело | прислать исправный файл |
| 401 | `UNAUTHORIZED` | нет или неверный ключ | заголовок `Authorization: Bearer <DRE_API_KEY>` |
| 413 | `UPLOAD_TOO_LARGE` | больше 20 МБ | уменьшить файл |
| 415 | `INVALID_PDF` | неподдерживаемый `Content-Type` | см. список типов выше |
| 422 | `UNREADABLE_DOCUMENT` | документ нельзя выдать без риска ошибок, причина в `details.reason` | см. таблицу ниже; обычно — пересканировать |
| 422 | `LANGUAGE_UNAVAILABLE` | письменность вне разрешённых (этап 1: кириллица и латиница) | — |
| 422 | `DOCUMENT_TOO_EXPENSIVE` | по прогнозу не успеть за 45 с (много страниц, медленная машина) или превышен лимит памяти | разделить документ, дать больше ядер |
| 503 | `SERVICE_BUSY` | все исполнители заняты | повторить запрос позже |
| 503 | `NOT_READY` | сервис загружается или не задан ключ | подождать `/ready` |
| 504 | `FAST_SLA_EXCEEDED` | не уложились в 45 с | разделить документ, дать больше ядер |
| 500 | `CONVERSION_FAILED` | внутренняя ошибка | прислать файл и `request_id` разработчикам |

Причины `details.reason` для `UNREADABLE_DOCUMENT`:

| `reason` | что значит |
|---|---|
| `low_resolution` | буквы меньше 8 px (`letter_height_px`): скан с низким разрешением или мелкий шрифт на фото |
| `unreliable_text` | есть слова, которые не удалось прочитать надёжно; в `words` — эти слова (текст\|второе чтение) |
| `unreliable_text_near_handwriting` | рядом с рукописной датой или номером печатный текст прочитан неуверенно |
| `unverifiable_text` | слишком много слов, которые нельзя проверить по словарю |
| `text_not_read` | большая часть текста на странице не распознана (`letters_read_share`) |
| `unrecognized_text` | часть страницы похожа на текст, но не распознана (другой алфавит, текст под печатью) |
| `unresolved_graphic_text_overlap` | печать или подпись закрывает текст, который не удалось прочитать |
| `unresolved_table_cells`, `unresolved_ruled_raster_table`, `unresolved_borderless_raster_table` | таблицу не удалось восстановить надёжно |
| `script_not_allowed_ocr`, `script_not_allowed_native` | текст на запрещённом алфавите (арабский, китайский на этапе 1) |
| `too_many_pages` | страниц больше `DRE_MAX_PAGES` |

`details.page_index` — номер страницы (с 0), на которой найдена проблема.

## 8. Логи

Сервис пишет в stderr (`docker logs`, журнал gunicorn) одну JSON-строку на каждую конвертацию:

```json
{"time": "2026-09-25T18:57:48+00:00", "request_id": "7b68…", "status": 422, "ms": 714,
 "code": "UNREADABLE_DOCUMENT", "reason": "low_resolution", "stage": "geometry", "page": 0, "pages": 1, "docx_bytes": null}
```

Содержимое документов в журнал не попадает. Пакетный режим пишет `OUT/journal.jsonl` и JSON рядом с каждым отказом.

## 9. Настройки (переменные окружения)

| переменная | по умолчанию | что делает |
|---|---|---|
| `DRE_API_KEY` | — (обязательна для сервиса) | ключ доступа к `/convert` |
| `DRE_OCR_ALLOWED_SCRIPTS` | `Latin,Cyrillic` | алфавиты для сканов и фото |
| `DRE_NATIVE_ALLOWED_SCRIPTS` | `Latin,Cyrillic` | алфавиты для PDF с текстовым слоем |
| `DRE_MAX_PAGES` | `10` | больше страниц — отказ до распознавания |
| `DRE_MIN_LETTER_PX` | `8` | порог высоты букв (px) для отказа `low_resolution` |
| `DRE_PAGE_THREADS` | `auto` | страниц одновременно (по ядрам и памяти, не больше 4) |
| `DRE_WORKERS` | `auto` | процессов-исполнителей: по ядрам + 1 тёплый запасной, если хватает памяти |
| `DRE_CONCURRENCY` | по ядрам | документов одновременно (на 1 ядре — 1; лишние запросы получают `SERVICE_BUSY`) |
| `DRE_WORKER_RSS_MB` | 8000 при памяти ≥ 16 ГБ, иначе 2200 + 400 на поток | предел памяти исполнителя (защита от утечки) |
| `DRE_SPEED_FACTOR` | измеряется при старте | задать множитель скорости вручную |
| `DRE_LEXICON_DIR` | `/app/lexicon` (Docker) | где лежат списки слов |

## 10. Обновление

Docker: собрать новый образ (`docker build -t dre:2 .`) или загрузить его (`docker load`),
запустить `docker run --rm dre:2 selfcheck`, затем заменить контейнер. Без Docker: получить новую
версию репозитория и повторить `sudo deploy/install.sh`, он переустановит окружение и выполнит самопроверку.
Одинаковый вход даёт одинаковый DOCX на любой машине с той же версией образа.

## 11. Медленное ядро (серверный Xeon)

- При старте модуль распознаёт эталонную страницу и сравнивает время с ядром ноутбука, на котором
  шли замеры (значение — в `/ready`, `ocr_capabilities.speed.factor`; 1.0 — как эталон, 1.5 — в полтора раза медленнее).
  Самопроверка печатает этот множитель и прогноз для одностраничного скана.
- До распознавания: прогноз = 3.3 с на страницу скана × множитель × 1.1 (на ноутбуке медиана 2.8 с, 95% страниц —
  до 4.8 с). Больше 45 с — сразу отказ `DOCUMENT_TOO_EXPENSIVE`, `reason: estimated_time_over_budget`.
  Сколько страниц скана укладывается: множитель 1.0 — до 11, 1.3 — до 9, 1.5 — до 7, 2.0 — до 5 (при `DRE_MAX_PAGES` 10).
- Во время работы: перед каждой следующей страницей — самая медленная страница этого документа × оставшиеся
  × 1.1 + 1.5 с должны уложиться в остаток времени, иначе тот же отказ сразу, а не таймаут в конце.
- Если нужный шаг проверки не успевает (перечитывание, третье чтение чисел), документ не выдаётся с
  непроверенным текстом: отказ по прогнозу. Медленная машина выдаёт меньше длинных документов,
  но выданные DOCX те же самые, что на быстрой.
- Проверено на ядре, загруженном наполовину (множитель 2.08): 1 и 3 стр. выданы за 5.5 и 17.5 с,
  7 и 10 стр. — отказ за 0.0 с; при намеренно заниженном прогнозе — отказ после первой страницы, не таймаут.

## 12. Чеклист на понедельник (рабочий сервер: 1 ядро Xeon, 128 ГБ, без GPU)

1. Клонирование (приватный репозиторий; частные образцы в репозитории нет — они в `samples-private.zip`):
   ```
   git clone git@github.com:<ORG>/dre.git && cd dre && git checkout v0.2.1-stage1
   ```
2. Сборка образа (5–10 мин; нужен только Docker, sudo не требуется, если пользователь в группе docker):
   ```
   docker build -t dre:0.2.1 .
   ```
3. Самопроверка на одном ядре — в конце должно быть `OK`:
   ```
   docker run --rm --cpus=1 dre:0.2.1 selfcheck
   ```
   Запишите строку `speed: {'factor': …}` — множитель скорости Xeon относительно ноутбука (1.0 — как ноутбук).
   Если он больше 1.3, длинные сканы будут чаще отклоняться по времени (раздел 11); прогноз для одностраничного
   скана должен быть меньше 45 с, иначе в выводе будет `NO`.
4. Ключ сервиса — только через окружение (образец: `.env.example`), никогда не в файлах репозитория:
   ```
   python3 -c 'import secrets; print(secrets.token_urlsafe(32))' > ~/.dre_key && chmod 600 ~/.dre_key
   docker run -d --restart=unless-stopped --cpus=1 -p 8080:8080 -e DRE_API_KEY="$(cat ~/.dre_key)" dre:0.2.1
   curl -s localhost:8080/ready
   ```
5. Пилот в режиме папки (без сервиса): положить документы в `~/pilot/in`, затем
   ```
   mkdir -p ~/pilot/out
   docker run --rm --cpus=1 --user $(id -u):$(id -g) -v ~/pilot:/data dre:0.2.1 batch /data/in /data/out
   docker run --rm -v ~/pilot:/data dre:0.2.1 summary /data/out
   ```
   Выданные DOCX — в `~/pilot/out`, отказы с причиной — в `~/pilot/out/_refused`, журнал — `journal.jsonl`.
   Первые 50–100 выдач просмотреть глазами (риски — `handoff/FINAL_REPORT.md`).
6. Необязательно: сверка с эталоном на тестовом наборе hires — распаковать `hires-rasters.zip` в корень
   репозитория и прогнать папку `handoff/samples/hires/scan_mild` (и др.) командой из шага 5: ожидается 74 выдачи из 75.
